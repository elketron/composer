composer: pipelines and the project view

Staged, reviewable work as a site: numbered stages with a contract each, scoped context for the stage worker, plain-file output you can edit, and gates where the pipeline asks for them. After Interpretable Context Methodology; the plan is phase 5 in plan.md. Same frame as the desktop and phone mockups.

The shape
  • A pipeline is a site (video, research, coding, made once from a template): what it is, its stage contracts in stages/, the shared rules in _config/, and one board app. The factory.
  • A piece of work is a folder in it (video/launch-video/): its brief, optional _config overrides, and a folder per stage with what the stage wrote. The product; doing it again is another folder.
  • A stage runs as a ticket with scoped context: the pipeline, its contract, its reference files, its working files. Nothing else. Chats and ordinary tickets are unchanged.
  • Gates live in the board app: the site's micro app shows the stages and writes Continue / Rerun / Stop into the stage's _stage.md; the server watches the page.
The project view

A project is always a folder on disk (~/Projects/game). Works in any pipeline link it, chats and orchestrators work in it, workers change it in worktrees. The project view puts all of that in one place, and the project scope narrows the session list and the palette to it.

Not in this round
  • Branching between stages (3a or 3b): a human choice at a gate for now (Rerun with a note, or Stop and start another pipeline).
  • Stages in parallel: sequential by design, as in the paper.
  • Archiving finished works out of the board: they stay as folders; a filter on the board for now.
